- 日期：2026-09-13。
- 状态：工程设计，尚未实现脚本、运行模型实验或获得专家验收。
- 目标：验证能否从一批文献的标题和原始摘要中，生成有来源依据、可供专家修订的研究问题目录。
- 结论边界：第一轮只评价指定语料上的可行性，不代表覆盖整个学科，也不证明所列问题尚未解决。

## 1. 最小交付物

第一版交付一个独立 Python 命令行实验工具，以及结构化结果和人工审阅表。一次运行完成：

```text
固定文献清单 -> 读取标题与原始摘要 -> 逐篇提炼问题并保存原句
             -> 问题向量化 -> 聚类 -> 归纳候选问题目录
             -> 输出来源、全部成员、未归组记录及审阅表
```

同时提供“直接聚类标题和摘要”的基线，验证逐篇提炼问题这一环节是否值得保留。原型成功后，再将数据读取、模型调用和任务管理接入 Java 应用。

## 4. 逐篇提炼的问题结构

文献与问题是一对多关系。默认每篇最多输出三个核心问题；超过上限或无法概括时显式标记，不静默截断。允许输出零个问题，并区分“摘要信息不足”和“处理失败”。

```json
{
  "document_id": "document-001",
  "status": "EXTRACTED",
  "questions": [
    {
      "question_id": "document-001:q1",
      "question": "示意问题表述",
      "research_object": "原文支持的研究对象",
      "question_origin": "INFERRED_FROM_OBJECTIVE",
      "source_field": "abstract",
      "evidence_quote": "与问题对应的摘要原句",
      "start_offset": 0,
      "end_offset": 12
    }
  ]
}
```

以上为结构示意，偏移位置必须由程序根据真实输入计算。冻结输入文本，记录偏移的字符计数约定；引用存在多处匹配时保留歧义并要求消歧。

提炼规则：

- 识别本文实际研究的问题，背景中提到的其他研究应单独处理。
- `EXPLICIT` 表示作者明确提出问题；`INFERRED_FROM_OBJECTIVE` 表示系统根据研究目的改写为问句。两者都必须有原句依据。
- 把“作者研究了什么”与“仍未解决什么”分开。本版不自动认定研究空白。
- 不提供 Q1–Q10 目录，不要求固定类别数量，不用模型的领域知识补充摘要未表达的问题。
- 程序检查 JSON、问题标识、原句位置和文献引用；人工检查原句在语义上是否支持问题。原句存在不等于问题归纳正确。

## 5. 聚类与目录生成

第一轮采用语义向量加凝聚层次聚类，使用 scikit-learn 的成熟实现。候选配置为 `metric="cosine"`、`linkage="average"`、`n_clusters=None`，通过开发集选择 `distance_threshold`。不将聚类数量设置为十类。

工程步骤：

1. 按问题 ID 排序，用“研究对象 + 研究问题”的文本生成向量。记录模型、维度及输入哈希；不混用不同向量模型的结果。
2. 检查有限数值、维度和零向量。失败的问题保留失败状态。零条或一条有效输入单独处理。
3. 聚类以问题为单位，同一文献可以通过多个问题进入不同组。单例和小组仍保留，标记为待归并。
4. 每组输入成员问题及其原句，让模型生成主题名和一至数个共同问题。每个共同问题必须引用实际成员 `question_id`。
5. 若组内不存在共同问题，标为 `NEEDS_SPLIT`。引用了不存在的成员或其他组成员时，校验失败。
6. 大组按固定预算分批，保留全部成员，明确哪些记录参与了归纳；不能只看少数代表论文却声称已概括整组。
7. 按去重文献数展示规模，同时保存全部问题记录。这个数只描述输入语料，不代表研究独立性或科学重要性。

目录条目至少包含：主题名、候选共同问题、文献数、代表文献、全部成员问题、摘要原句、待审状态。专家先通过审阅表给出保留、改名、合并、拆分和不支持等决定。

scikit-learn 参数依据：[AgglomerativeClustering 官方文档](https://scikit-learn.org/stable/modules/generated/sklearn.cluster.AgglomerativeClustering.html)。具体距离阈值没有跨模型通用的默认正确值。

## 6. 最小实验

### 6.1 输入

先用 10 篇文献调通引用、状态、费用记录和输出格式，再选取约 100 篇有可用摘要的去重文献开展首轮实验。该规模为预算起点，不构成统计功效保证。

抽样覆盖多个研究方向和年份，避免只使用已经被 Q1 分类通过的文献。记录语料来源、去重及缺摘要数量。已有 Q1–Q10 标签可用于事后检查，不进入发现提示词。

可将 20 篇作为开发材料，剩余 80 篇作为参数冻结后的评价语料。重复报告应尽量归于同一集合。对评价语料重新形成目录，不根据其人工评价调参后继续将其称为独立测试。

### 6.2 对照

| 方案 | 输入表示 | 后续处理 |
| --- | --- | --- |
| A：直接摘要聚类 | 标题 + 原始摘要，每篇一个向量 | 聚类、根据成员摘要归纳问题目录 |
| B：先提炼问题 | 摘要中提炼的各项问题，每篇可多个向量 | 同类聚类算法、根据问题及原句归纳目录 |

两组用相同原始文献、相同向量模型和相同目录归纳模型，采用相同的调参预算；记录 B 增加的调用成本。A 与 B 的聚类单位不同，因此按原始文献上的问题覆盖及目录可用性比较，不直接把簇内分数作为胜负指标。

至少抽取 30 篇评价文献，由领域人员先独立列出摘要支持的研究问题，再查看匿名化的 A/B 输出。由另一人复核或裁决。人工参考先于模型输出建立。

### 6.3 可行性判定

下面是初步试点门槛，正式运行前由项目负责人和领域专家冻结，不能根据结果事后修改。

| 指标 | 定义 | 初步门槛 |
| --- | --- | --- |
| 引用可定位 | 所有展示的问题均可经成员记录回到输入原句 | 100% |
| 问题有依据 | 人工审阅的问题中，摘要确实支持其表述的比例 | 至少 90% |
| 问题覆盖 | 人工列出的参考问题中，系统目录能通过对应文献成员覆盖的比例 | 至少 80% |
| 归组合理 | 抽查“问题—所属主题”关系中，专家认可的比例 | 至少 80% |
| 目录可用 | 只需保留或文字调整的目录条目占全部条目的比例 | 至少 80% |

分别报告分子、分母、未输出数量、单例比例、失败率、耗时与费用。审查跨组重复，并检查专家认为相近的问题是否被拆散，避免全部单例看起来“归组正确”。

评价覆盖率时，从全部抽样文献出发：无输出、解析失败和问题提炼失败也进入统计。归组与目录质量按组大小分层抽查，不能只检查最大的几个组。

软件测试重点是：引用错配、不存在的成员 ID、重复文献、零/单条输入、无摘要、模型返回非法 JSON、向量失败，以及修改模型/提示词/输入后不得误用旧缓存。这些测试通过只证明实现约束成立。

为检查稳定性，固定输入和软件配置后额外进行少量独立问题提炼运行，报告问题及归组变化；读取同一缓存不是稳定性实验。

### 6.4 决策

- A 已满足人工使用要求，B 没有改善覆盖、目录质量或整理时间：优先保留 A 的简单流程。
- B 有依据、覆盖足够，并改善目录质量或减少专家整理工作：支持继续接入正式系统。
- 问题经常无依据：优先检查问题提炼及摘要是否足够表达研究目的。
- 问题正确但归组混乱：检查问题表述、向量表示和聚类阈值。
- 归组合理但共同问题空泛：检查归纳提示词和主题粒度。
- 大量文献无摘要或信息不足：记录适用范围，再用引言/全文补充做单独对照。

## 7. 成功后的工程接入

确认上述实验有使用价值后，再增加 Java 实验服务和异步运行入口，复用文献仓库、模型封装、向量模型及已有任务执行模式。将文件中的运行记录、问题、主题成员和专家修订迁入持久化存储，并增加审阅界面。

专家批准的问题目录可以作为后续字段设计的输入；它不自动替换现有 Q1–Q10 prompt。正式字段规范仍需要定义语义、缺失状态、适用条件与全文证据要求。

迁移到第二个学科时复用同一流程、记录实际修改量，才能开始评价通用性。卵菌语料上的一次成功只能支持本领域首轮可行性。
